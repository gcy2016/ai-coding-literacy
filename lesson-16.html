第 16 节

GitHub：分支与协作

1 一句话结论
GitHub 是大家围着同一份代码协作的地方。

2先打个比方：平行世界与合并

主线（main，大家共用的正式版本）好比一条主路。想试一个大改动，先旁开一条岔路随便折腾，主路照常通行；岔路上验证没问题，再并回主路。并的时候像审修订稿：改动一行行红绿对照摆出来，看过、点头，才算数。

图：分支（branch）与合并（merge）——岔开、验证、并回

3正文

分支：另开一条线改，不影响主线。分支（branch）是从主线某个存档点岔出去的一条独立线。在分支上怎么改、怎么提交，主线都纹丝不动；改砸了删掉分支就行，改好了再申请并回去。大改动、试验性改动，都该先上分支。

1从主线岔出一条分支
↓
2在分支上改、提交、验证
↓
3发合并请求，请人审查
↓
4审查通过，合并回主线

合并请求：先审后并的那道关。合并请求（Pull Request，简称 PR）就是「我这条分支改好了，申请并回主线」。它不会立刻生效：审查的人把这次改动逐行看过、讨论过、点了同意，才真正合并。这道关拦的是「没人看过的大改动直接上线」。

Issue 和冲突：记事本和撞车。Issue（问题帖）是仓库里的记事本：需求、问题、待办都开帖记下，逐条讨论、逐件销账，不靠口头传话。冲突（conflict）则是两条线改了同一处、合并时 Git 判不了谁对，就停下来等人裁决，绝不自作主张。

.gitignore 和 diff：一个管不进、一个管看清。.gitignore（忽略清单）写明哪些文件不许进仓库，密钥、临时文件都列里面，防误传。看改动靠 diff（差异对照）：删掉的行标红、新增的行标绿，改了哪几行一目了然，审查主要看它。

diff 长这样意思
- 旧的一行（红色）这一行被删掉了
+ 新的一行（绿色）这一行是新加的

4对应到你的项目：CANLink 的协作实录

问题全记在 Issue 里。CANLink 攒下的问题都记在 AI_Corp 仓库的第 12 号 Issue 里：一条评论派一件活、一条回复报一个结果，哪件做完、哪件还欠着，翻帖子就清楚，不靠谁记性好。

两种节奏都是真的。canlink 的 BLF 导出是个不小的功能，当时走了第 23 号 Pull Request：开分支写好、审查确认没问题，才合并进主线。而平时的日常小改——改个文案、修个小毛病——是直接推主线的。重要的走 PR 把关、小改直推图快，这不是偷懒，是按风险分级。

5和 AI 协作时怎么用

可以这样说「这个改动不小，先开分支走 PR，我看过 diff 再合并。」
可以这样说「问题先记到 Issue 里，一件一件来，别口头说完就忘。」
可以这样说「合并之前把 diff 发我看，确认只改了该改的地方。」
别这样说「这个大改动也直接推主线吧，不用审了。」——小改直推没问题，大改动跳过审查，出事时连改了哪几行都没人看过。

7小测（选完立刻看对错）

1. 分支是用来干什么的？
解析：分支就是岔路：上面怎么折腾，主线都照常能用；验证好了才并回来。
2. 合并请求（PR）最关键的一步是什么？
解析：PR 的价值在那道审查关——大改动没人看过就上线，风险全裸奔。
3. 看 diff 时发现一大片红色的行，说明什么？
解析：diff 里红色是删除、绿色是新增。大片红色先别慌，看清删的是不是该删的。
4.（情景）两个 AI 先后改了同一段代码，合并时 Git 报了冲突。你该怎么办？
解析：冲突是 Git 在喊「这处我判不了」。随便覆盖等于闭眼扔掉一份改动，必须人工裁决。
5. 密钥文件为什么要提前写进 .gitignore？
解析：.gitignore 是「不许进仓库」的名单。密钥一旦提交进历史，想撤干净非常麻烦，所以要从源头拦住。
