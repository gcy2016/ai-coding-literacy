第 15 节

Git：给代码存档

1 一句话结论
Git 是代码的存档点：改动可存、可查、可退。

2先打个比方：游戏存档点

玩游戏打大 Boss 之前先存个档，打输了读档重来，不用从头再玩。Git（一种分布式版本控制工具，专管代码的历史记录）就是给代码装的存档系统：每改一段就存一个档，存档连成一条线，哪个档是好的、哪个档出了问题，一翻记录全知道。

图：提交就是存档点，历史记录就是存档列表

3正文

仓库和提交：存档装在哪、怎么存。仓库（repository）就是项目文件夹外加它的全部历史。提交（commit）就是一次存档：把当前改动打包记下，再附一句说明——改了什么、为什么改。存档多了，连起来就是历史记录（history）。

存档（提交）说明写的什么
存档一项目初始化
存档二修复登录页按钮错位
存档三新增深色模式（这版有问题）

本地与远程：同一代码，两份副本。本地（local）是你电脑上的那份，改和提交都在这里；远程（remote）是 GitHub 上的那份，是共用的正本。两份靠推送和拉取同步：推送（push）把本地新提交送上远程，拉取（pull）把远程新提交取回。

本地远程
在哪自己的电脑GitHub 上
干什么改代码、提交共用正本、备份
怎么同步推送 push 送上去 · 拉取 pull 取回来

回到上一个版本：两种退法。改坏了不用慌，历史里每个版本都在。一种是读档重来（reset，把进度直接拨回某个旧存档，后面的当没发生过）；一种是补一次「反悔存档」（revert，新提交一次，内容正好是把上次改动抵消掉，历史不删、账目清楚）。

reset读档重来，历史改写
revert补一次反悔，历史保留

为什么 AI 改代码离不开它。AI 改得快，也可能改坏。有了 Git，每次改动前有存档、改动后有说明，出了问题能精确定位是哪一次改坏的、退回哪一步。没有这套东西，AI 改一百行出了错，你只能对着一团乱麻发呆。

4对应到你的项目：这门课的仓库

你现在看的这门课，每一次上线都是一次提交。仓库有变更记录制度：提交说明必须写清谁改的、改了什么、为什么改——以后翻历史，不用猜当时发生了什么。

今天（2026-11-12）就出过一次真实的推送被拒：远端的仓库里已经有了新的提交，这边没先拉取就直接推送，Git 当场拦下——它怕你把别人的新改动盖掉。先拉再推，就没事了。这正是 Git 的脾气：宁可拦你一下，也不许互相覆盖。

5和 AI 协作时怎么用

可以这样说「动手改之前先提交一次，改坏了我能退回来。」
可以这样说「推送之前先拉取一下，看远端有没有新的提交。」
可以这样说「这次提交的说明写清楚：谁改的、改了什么、为什么。」
别这样说「直接覆盖上去就行，不用管远端。」——远端可能有别人刚提交的改动，覆盖掉就找不回来了。

7小测（选完立刻看对错）

1. Git 最核心的本事是什么？
解析：Git 是版本控制工具，管的是「历史」：谁改的、改了什么、怎么退回去。
2. 一次「提交」到底是什么？
解析：提交就是存档点。说明写清改了什么、为什么，以后翻历史才看得懂。
3. 本地仓库和远程仓库是什么关系？
解析：本地在你电脑上、远程在 GitHub 上；push 送上去，pull 取回来。
4.（情景）AI 说：「推送被拒了，远端已经有新的提交。」你应该让它怎么做？
解析：被拒是 Git 在防互相覆盖。先 pull 再 push，新改动两边都不丢。
5. AI 把功能改坏了，想回到昨天那个好用的版本，靠的是什么？
解析：每个版本都在历史里。reset 是读档重来，revert 是补一次「反悔存档」，都能回到好用的状态。
